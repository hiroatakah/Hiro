# 04. プロダクト・アーキテクチャ：7層スタックと開発優先順位

> **本ドキュメントは「何を作り、何を作らないか」の定義書です。**

## 1. OneWay Enterprise AIOS 7層アーキテクチャ

```
┌───────────────────────────────────────────────────┐
│  T1   OneWay Control Center                        │  ★最大の差別化
│       利用状況 ｜ ROI ｜ 監査 ｜ コスト ｜ 権限        │  経営者が見る画面
├───────────────────────────────────────────────────┤
│  T2   AI Agent Layer                               │  ★資産（Library）
│       営業 ｜ 人事 ｜ 経理 ｜ CS ｜ 経営 ｜ 店舗       │
├───────────────────────────────────────────────────┤
│  T3   Workflow Layer                               │
│       承認 ｜ 通知 ｜ 入力 ｜ 処理 ｜ 記録             │
├───────────────────────────────────────────────────┤
│  T4   Knowledge Layer                              │  ★価値の源泉
│       社内規程 ｜ マニュアル ｜ FAQ ｜ 契約書          │
├───────────────────────────────────────────────────┤
│  T5   AI Gateway / Governance                      │  ★エンタープライズの関門
│       認証 ｜ 権限 ｜ ログ ｜ 安全性 ｜ モデル選択      │
├───────────────────────────────────────────────────┤
│  T6   Enterprise Systems（既存システム）             │  接続するだけ
│       CRM ｜ ERP ｜ 勤怠 ｜ メール ｜ チャット         │
├───────────────────────────────────────────────────┤
│  T7   AI / Cloud（外部基盤）                        │  絶対に作らない
│       OpenAI ｜ Claude ｜ Gemini ｜ AWS 等           │
└───────────────────────────────────────────────────┘
```

## 2. 層ごとの「作る／作らない」判断

| 層 | 差別化度 | 方針 | 理由 |
|---|---|---|---|
| **T1** Control Center | **極高** | **独自開発（最優先）** | 経営者向けAIダッシュボードは、この市場にまだ存在しません |
| **T2** AI Agent Layer | 高 | **独自開発（資産化）** | 中身（業種別の型）が差別化。実行エンジン自体は差別化しません |
| **T3** Workflow Layer | 中 | 薄く自作 + 既存連携 | 承認・通知は既存ツール（Slack/Teams/kintone等）に寄せます |
| **T4** Knowledge Layer | 高 | **独自開発** | 技術ではなく**運用設計**（鮮度管理・権限連動）が差別化 |
| **T5** AI Gateway / Governance | **極高** | **独自開発（最優先）** | ここが通らないとエンタープライズは1社も導入できません |
| **T6** Enterprise Systems | 低 | **接続のみ。作らない** | 既存システムには手を入れません |
| **T7** AI / Cloud | ゼロ | **絶対に作らない** | モデル・インフラの自社開発は、体力的にも戦略的にも誤りです |

> **「T7を作らない」を明文化する理由：**
> AI企業を名乗ると、必ず「独自モデルは作らないのか」と聞かれます。答えは明確に「作りません」です。
> **OneWayの堀はモデルではなく、T1（経営可視化）・T5（統制）・T2（業種別の型）にあります。**
> モデルは3年で陳腐化しますが、企業の業務知識とガバナンス設計は陳腐化しません。

## 2.5 AIOSの2大中核資産：Company DNA と AI Value Ledger

7層スタックの上に、OneWay Enterprise AIOS を「経営OS」たらしめる2つの資産を定義します。**プロダクト名であると同時に、堀（[05](05-ecosystem-model.md) 第7.5章）の第1・第3層です。**

### 2.5.1 Company DNA（T3・T4・T5を貫く中核データ資産）

**その会社が「どう判断し、どう仕事をする会社なのか」を、AIが理解できる形に構造化したもの。** 最も他社に真似されにくい資産です。

| 構造化する10要素 | 格納先の層 |
|---|---|
| 業務フロー ／ 例外処理 | T3 Workflow |
| 社内規程 ／ 過去事例 ／ 顧客対応方針 ／ ナレッジ | T4 Knowledge |
| 意思決定ルール ／ 承認ルール ／ 役割 ／ 権限 ／ KPI | T5 Governance |

**設計原則：**

1. **初期構築はAssessment（Level 1）の9工程が担います。** 300万円の診断は、実はCompany DNAの初期採取でもあります
2. **Company DNAは顧客に帰属します。** ただし記述形式（スキーマ）はOneWayの標準です。**データは顧客のもの、形式はOneWayのもの** — これが乗り換え障壁と信頼を両立させる線引きです
3. 更新は四半期レビューで行い、**「DNAが古い会社のAIは間違える」**ことを更新継続の理由にします

### 2.5.2 AI Value Ledger（T1 Control Center の中核機能）

**「AI P&L」— AI社員別・業務別の投資対効果を、会計帳簿のように記録する台帳です。**

| 記録単位 | 記録内容 |
|---|---|
| AI社員（エージェント）別 | 実行回数 ／ 削減時間 ／ AIコスト ／ 粗効果額 ／ 純効果額 |
| 業務別・部門別 | 自動処理件数 ／ 人の介在率 ／ エラー率 |
| 経営集計 | 投資累計 ／ 効果累計 ／ ROI ／ 回収進捗（Assessment時の試算との対比） |

**戦略的意味：** ①更新稟議の根拠を経営者の手元に常設する ②「Assessmentで約束した数字」との突合が信頼を作る ③**匿名化集計が業界ベンチマーク（堀④）の原料になる**（利用統計の匿名利用は契約条項で担保済み）

## 3. 最初に開発する4プロダクト

### 3.1 全体像と依存関係

```
      ③ OneWay Governance  ←── 全ての前提（これがないと1社も入らない）
              │
              ▼
      ② OneWay Knowledge Hub  ←── エージェントが賢くなる燃料
              │
              ▼
      ① OneWay AI Catalog  ←── 顧客が最初に価値を感じる場所
              │
              ▼
      ④ OneWay AI Control Center  ←── 経営者に見せる / 更新率を守る装置
```

**依存関係の要点：** ③→②→① の順で技術的に必要ですが、**顧客が価値を感じる順は ①→④** です。この2つのズレをどう扱うかが開発計画の核心です。

**結論：③と②は最小構成で先に作り、①で価値を見せ、④で経営を握ります。**

---

### 3.2 ① OneWay AI Catalog

**企業内で使えるAIエージェントの一覧・実行環境。顧客が最初に触れる場所です。**

| 項目 | 内容 |
|---|---|
| 役割 | エージェントの発見・実行・共有 |
| 顧客価値 | 「何ができるか」が一覧で分かる。導入初日から使えます |
| 戦略的役割 | **EL3（AI Agent Library）の実体。標準の器** |

**初期カタログ（横断12種 + 業種別）：**

| 部門 | エージェント |
|---|---|
| 営業 | 営業議事録AI / 提案書AI / 見積AI |
| CS | 問い合わせAI / クレーム一次対応AI |
| 管理 | 契約書確認AI / 経理照会AI / 勤怠確認AI |
| 人事 | 採用AI（求人票・スカウト・面談記録） |
| 経営 | 経営会議AI（資料要約・論点抽出） |
| 店舗・現場 | 店舗報告AI / 日報集計AI |

**業種別追加（[02-icp-target.md](02-icp-target.md) 3.2 に対応）：** 不動産問い合わせAI / 介護記録AI / 物流荷主対応AI / 建設安全書類AI 等

**最重要の設計事項：エージェント記述仕様を先に決めます。**

```yaml
# エージェント定義の標準形式（例）
agent:
  id: sales-meeting-minutes
  name: 営業議事録AI
  category: 営業
  industry: [共通]
  inputs:    [音声ファイル, 参加者リスト]
  outputs:   [議事録, ネクストアクション, CRM登録用データ]
  knowledge: [商品マスタ, 過去議事録]
  permissions: [営業部門, 営業企画]
  approval:  不要
  eval:      [必須項目の充足率>=95%, 固有名詞の誤り0件]
  effort_saved: 30分/件
```

> **仕様を決める前に本数を増やしてはいけません。** 形式がバラバラだと、資産にもならず、パートナーも作れず、Marketplaceも成立しません。**本数より仕様が先です。**

---

### 3.3 ② OneWay Knowledge Hub

**社内文書・マニュアル・規程をAIから利用できる共通知識層。**

| 項目 | 内容 |
|---|---|
| 役割 | 社内文書の取込・構造化・検索・**鮮度管理** |
| 対象文書 | 社内規程 / 業務マニュアル / FAQ / 契約書雛形 / 商品資料 / 過去の提案書 |
| 顧客価値 | 「うちの会社のことを知っているAI」になります |

**差別化は技術ではなく、次の3点の運用設計にあります：**

| # | 論点 | OneWayの設計 |
|---|---|---|
| 1 | **鮮度管理** | 文書に有効期限と更新責任者を持たせ、期限切れを検知して通知します。**放置された知識層は3ヶ月で腐ります** |
| 2 | **権限連動** | 人事規程は人事部のみ、といった閲覧権限をAI出力にも継承します |
| 3 | **出典明示** | 回答に必ず出典文書とバージョンを付与します。エンタープライズでは根拠のない出力は使えません |

**MVP範囲：** 主要文書500〜2,000件の取込 / 全文検索 + 意味検索 / 出典表示 / 権限フィルタ

### 3.4 ③ OneWay Governance

**誰が、何のAIで、何のデータを、何に使ったかを管理します。**

> **エンタープライズにおいて、ここが価格を上げる最大の要素です。**

| 機能 | 内容 | なぜ価格が上がるか |
|---|---|---|
| **認証・権限** | SSO（SAML/OIDC）/ 部門別・役職別の権限マトリクス | 情シスの承認要件 |
| **監査ログ** | 誰が / いつ / 何を入力し / 何を出力したか の全記録 | 内部統制・監査対応の必須要件 |
| **入力統制** | 機密情報・個人情報の検知とブロック | 情報漏洩リスクの遮断 |
| **モデル選択** | 用途別のモデル振り分け・ベンダー選定基準 | コスト最適化 + ベンダーロックイン回避 |
| **承認フロー** | Human-in-the-loop。重要出力は人間承認を必須化 | 誤出力の業務影響を遮断 |
| **利用規程** | AI利用ガイドラインの雛形と社内展開支援 | 法務の承認要件 |

**この層がない提案は、情シス・法務の審査で必ず止まります。** 逆に、この層を最初から持っていることが、零細AIベンダーとの決定的な差になります。

---

### 3.5 ④ OneWay AI Control Center

**経営者向けダッシュボード。独自UIとして最も力を入れる領域です。**

| 表示指標 | 内容 |
|---|---|
| **AI利用量** | 部門別・エージェント別の実行回数、アクティブ利用率 |
| **削減時間** | 実行回数 × エージェント別の想定削減時間の積算 |
| **AIコスト** | 消費クレジット / 部門別コスト配賦 |
| **自動処理件数** | 人手を介さず完了した処理の件数 |
| **推定ROI** | 削減時間の金額換算 ÷ 投資額 |

**Control Center が持つ3つの戦略的機能（ダッシュボード以上の意味があります）：**

| # | 機能 | 効果 |
|---|---|---|
| 1 | **更新率を守る装置** | 更新判断の3ヶ月前、経営者は「これは効果があったのか」を必ず問います。**その答えを常時表示しておくことが、最強の解約防止策です** |
| 2 | **Expand（単価上昇）の装置** | 部門別実績が見えると、実績の低い部門・未導入部門が可視化されます。**社長自ら横展開を指示します** |
| 3 | **営業の装置** | 既存顧客の実画面（匿名化）を新規商談で見せます。**「導入するとこれが見えます」は、どんな提案書より強い** |

> **Control Center は、機能としては地味です。しかし、この4つの中で最も事業インパクトが大きいプロダクトです。**

## 4. 開発ロードマップ

### 4.1 90日MVP（Phase 0〜1：最初の1社を動かす最小構成）

| 期間 | 開発内容 | 完成基準 |
|---|---|---|
| Day 1-30 | **③ Governance 最小版**（認証・権限・全実行ログ）<br>**② Knowledge Hub 最小版**（文書取込・検索・出典表示） | 情シスの技術審査を通過できる状態 |
| Day 31-60 | **① AI Catalog v1**（横断エージェント10種 + 記述仕様v1） | 顧客部門が実業務で使える状態 |
| Day 61-90 | **④ Control Center v1**（利用量・削減時間・ROIの3指標） | 経営会議で報告できる状態 |

**90日目に「経営会議で成果を報告できる」ことが唯一の合格基準です。**

### 4.2 Year 1〜2

| 時期 | 開発内容 |
|---|---|
| Y1後半 | Catalog 30種へ拡充 / 業種別エージェント（重点3業種）/ Workflow 最小版（承認・通知） |
| Y2前半 | **エージェント記述仕様 v2 を外部公開**（パートナーが作れる状態に）/ Governance 拡充（入力統制・モデルルーター） |
| Y2後半 | Control Center 拡充（部門別配賦・予測）/ T6 主要システム連携（CRM・勤怠・チャット） |
| Y3 | パートナー向け開発環境 / Marketplace 基盤の設計着手 |

## 5. 技術選定の原則

| 原則 | 内容 |
|---|---|
| **1. モデルは複数ベンダーを使い分ける** | 単一ベンダー依存は価格・可用性・規約変更のリスクです。T5のモデルルーターで抽象化します |
| **2. 顧客ごとにコードを書かない** | 顧客別要件は設定・テンプレートで吸収します。**この一線を越えたら受託会社に戻ります** |
| **3. 顧客テナントは分離する** | 中堅企業でもデータ分離は必須要件です。共通環境は提案段階で必ず論点になります |
| **4. オンプレ／VPC対応は Level 4 以上に限定** | 安易に受けると、運用コストが利益を食い潰します |
| **5. 既存システムには手を入れない** | T6への書き込みは最小限に。障害時の責任範囲が無限に広がります |
| **6. 自社でモデルを訓練しない** | 費用対効果が合いません。差別化は業務知識とガバナンスに集中します |

## 6. 「作らないもの」リスト（意思決定を速くするために明文化）

| 作らないもの | 代替 |
|---|---|
| 独自の基盤モデル | 外部モデルをルーティングして使います |
| クラウドインフラ | 既存クラウドを利用します |
| CRM / ERP / 勤怠システム | 既存システムに接続します |
| チャットツール | Slack / Teams に組み込みます |
| BIツール全般 | Control Center は AI利用に特化した指標のみ扱います |
| 顧客専用のカスタム機能 | 設定・テンプレート・次期ロードマップのいずれかで吸収します |
