## 0. 【重要】3つの「階層」を混同しないこと

OneWay の戦略には、性質の異なる3つの階層構造が同時に存在します。**会話の中でこれらを取り違えると、議論が噛み合わなくなります。**

| 呼称 | 何の階層か | 記号 | 定義文書 |
|---|---|---|---|
| **事業エコシステム** | 会社が保有する事業レイヤー | **EL1〜EL6** | **本ドキュメント** |
| **商品ラダー** | 顧客の契約単価を上げる段階 | **Level 0〜5** | [03-product-ladder.md](03-product-ladder.md) |
| **技術アーキテクチャ** | プロダクトの技術スタック | **T1〜T7** | [04-architecture.md](04-architecture.md) |

**対応関係：**

```
事業レイヤー EL2（AI Platform）を
  → 商品ラダー Level 3〜5 として売り
    → 技術アーキテクチャ T1〜T5 で実装する
```

## 2. フライホイール：なぜ各レイヤーが次を起動するのか

**このモデルの本質は「積み上げ」ではなく「循環」です。**

| # | 起動関係 | メカニズム |
|---|---|---|
| 1 | **EL1 → EL2** | 設計を握ると、その設計を実装する基盤は必然的にOneWay製になります。設計者が土台を指定するのは自然だからです |
| 2 | **EL2 → EL3** | プラットフォームが「エージェントの置き場所」になります。置き場所がなければライブラリは成立しません |
| 3 | **EL3 → EL4** | パートナーが売れる商材（＝標準化されたエージェント）ができて初めて、パートナーが集まります。売るものがなければ誰も参加しません |
| 4 | **EL4 → EL5** | パートナーが増えると品質のばらつきが問題になります。そこで初めて認定制度に需要が生まれます |
| 5 | **EL5 → EL6** | 認定という品質保証があるから、第三者の作った資産を安心して売買できます。保証なき市場は成立しません |
| 6 | **EL6 → EL1** | 市場に集まった企業が「うちも導入したい」と言い出します。その入口は必ず設計（EL1）です |

> **円環が一周した瞬間、OneWayは「営業しなくても案件が来る会社」になります。**
> 逆に言えば、一周するまでは営業し続ける必要があります。ここを誤解しないでください。

## 3. レバレッジの階段：なぜ従業員を増やさずに済むのか

| レイヤー | 収益源 | OneWayの人的依存 | スケール手段 | 粗利率目安 |
|---|---|---|---|---|
| **EL1** Strategy | 設計フィー | **最高**（Hiro依存） | フレームワーク化・テンプレート化 | 70% |
| **EL2** Platform | 年間利用権（ARR） | 中 | ソフトウェア（複製コストゼロ） | 65〜75% |
| **EL3** Library | 資産利用権・追加販売 | 低 | 資産の複製 | 85% |
| **EL4** Partners | 年会費・レベニューシェア | 低 | **他社の人員** | 90% |
| **EL5** Certification | 受験料・研修費・更新料 | 極低 | 制度（一度作れば回る） | 85% |
| **EL6** Marketplace | 取引手数料 | 極低 | ネットワーク効果 | 95% |

**下のレイヤーほど、OneWayの人員を使わずに売上が立ちます。**

これが「従業員を大量に抱えず、高単価Enterprise案件を扱う」の実装です。精神論ではなく、収益源の構成比を変えることで達成します。

**目標構成比：**

| | Y1 | Y3 | Y5 |
|---|---|---|---|
| EL1 Strategy | 38% | 12% | 6% |
| EL2 Platform | 62% | 68% | 52% |
| EL3 Library | 0% | 14% | 16% |
| EL4 Partners | 0% | 6% | 13% |
| EL5 Certification | 0% | 0% | 5% |
| EL6 Marketplace | 0% | 0% | 8% |

## 4. レイヤー別プレイブック

### EL1 — AI Strategy（戦略・設計層）

**エコシステムの入口。ここだけは絶対に他社に渡してはいけません。**

| 項目 | 内容 |
|---|---|
| **売るもの** | AI活用アセスメント / エンタープライズAIアーキテクチャ設計 |
| **価格** | Executive AI Briefing 50〜100万円 / **Enterprise AI Assessment 300万円**（4〜6週間） |
| **顧客** | 経営層（CEO / CIO / 経営企画） |
| **提供者** | Hiro（当面）→ 認定AIアーキテクト（将来） |
| **成果物** | 業務プロセスマップ / ユースケース優先順位 / ROI試算 / ガバナンス方針 / 90日実装計画 |
| **戦略的役割** | **設計を握ることで、EL2以下の採用を実質的に確定させます** |

**核心資産：OneWay AI Architecture Framework（OAF）**

自社の設計手法を、他社が参照できる形で文書化・公開します。

- 公開する理由：**標準は、使われて初めて標準になります。** 秘匿すると標準になりません
- 参照モデル：AWS Well-Architected Framework が無料公開されている理由と同じ構造です
- 構成案：①業務適用領域の評価軸 ②ガバナンス成熟度モデル（5段階）③エージェント設計原則 ④ナレッジ基盤の設計基準 ⑤ROI測定の標準指標

**着手時期：即時（Phase 0）**

**KPI：** Assessment 受注件数 / Assessment→Platform 転換率（目標60%）/ OAF の外部参照数

**禁則：**
- 設計をパートナーに委譲しない。入口を失います
- 無料の設計提案をしない。有償アセスメントに一本化します

### EL2 — AI Platform（基盤層）

**収益の背骨。ARRを積む唯一のレイヤーです。**

| 項目 | 内容 |
|---|---|
| **売るもの** | OneWay Enterprise AI Platform の年間利用権 |
| **価格** | Department 1,000〜2,000万円 / **Enterprise 3,000〜8,000万円** / Enterprise Agreement 年3,000〜8,000万円×3年 |
| **含むもの** | AI Catalog / Knowledge Hub / Governance / Control Center / 継続アップデート / 運用支援 |
| **戦略的役割** | ①ARRの源泉 ②EL3の置き場所 ③顧客ロックイン |

**絶対原則：顧客ごとにコードを書きません。**

顧客別要件は Configuration（設定・テンプレート）で吸収します。この一線を越えた瞬間、OneWayは受託会社に戻ります。

詳細は [04-execution-plan-36m.md](08-execution-plan.md) 第2章。

**着手時期：即時（Phase 0〜1）**

**KPI：** ARR / NRR / 週次アクティブ利用率（40%が生命線）/ Time to First Value

### EL3 — AI Agent Library（資産層）

**最も見落とされやすく、最も重要なレイヤーです。ここが「標準」の実体になります。**

| 項目 | 内容 |
|---|---|
| **売るもの** | エージェント・業務テンプレートの利用権、追加パック |
| **価格** | コア10種を同梱 / 汎用 月5万円 / 業種特化 月10万円 / 高度 月20万円（1Agentあたり） |
| **供給源** | ① OneWay製 ② パートナー製 ③ 顧客製 |
| **戦略的役割** | **エコシステムの通貨。EL4とEL6を成立させる前提条件** |

**このレイヤーの本当の価値は、収益ではありません。**

> **エージェントの「記述形式（仕様）」を OneWay が定義することです。**

仕様を持つ者が、事実上の標準を持ちます。以下を定義します。

| 定義すべきもの | 内容 |
|---|---|
| **エージェント記述仕様** | 入力 / 出力 / 権限 / 依存ナレッジ / 承認要否 / 評価基準 をどう書くか |
| **テンプレート形式** | 業務手順をどう構造化して記述するか |
| **品質基準** | 何をもって「動作する」とするか（Eval の合格基準） |
| **メタデータ** | 業種 / 職種 / 難易度 / 前提条件 / 想定効果 |

**進化の3段階：**

```
第1段階（Y1-Y2）：OneWay製のみ         ── 単なる「機能一覧」
        ↓
第2段階（Y3-Y4）：パートナー製が加わる  ── 「ライブラリ」になる
        ↓
第3段階（Y5-）  ：顧客製・売買が発生    ── 「マーケットプレイス」になる（EL6）
```

**第2段階に入った瞬間、OneWayの商品開発力は自社の人員から解放されます。** これがEL3の戦略的核心です。

**着手時期：Phase 1 から蓄積開始、Phase 2 で仕様公開**

**KPI：** ライブラリ本数 / 1社あたり稼働ユースケース数 / パートナー製の比率 / 追加パック販売額

**禁則：**
- 顧客案件で作ったものを汎用化せず放置しない。**Phase 1 の最大の成果物はライブラリです**
- 仕様を決める前に本数を増やさない。形式がバラバラだと資産になりません

### EL4 — Implementation Partners（実装パートナー層）

**ここで初めて「従業員を増やさずにスケール」が成立します。**

| 項目 | 内容 |
|---|---|
| **売るもの** | パートナー年会費 / レベニューシェア / 認定研修 |
| **価格** | Silver 年50万円 / Gold 年150万円 / Platinum 年300万円 + レベニューシェア15〜20% |
| **戦略的役割** | 実装工数・与信・顧客接点を他社から調達します |

**3種のパートナー（役割が違うので混同しないこと）：**

| 種別 | 担うもの | 具体例 | OneWayが得るもの |
|---|---|---|---|
| **実装パートナー** | 実装工数 | 中堅SIer / システム開発会社 / Web制作会社 | 人員を増やさずにデリバリー能力を拡大 |
| **販売パートナー** | 接点と与信 | 税理士法人 / 会計事務所 / 地銀・信金 / 経営コンサル | **設立間もないOneWayに欠けている信用** |
| **業務パートナー** | ドメイン知識 | 業界特化コンサル / 士業 / 業界団体 | 業界別パッケージの中身 |

**最重要の戦略的洞察：開発会社を敵にせず、流通網に変えます。**

システム開発会社はOneWayの競合に見えますが、**彼ら自身も受託の限界（人月の頭打ち・継続収益のなさ）に苦しんでいます。**

OneWayの基盤に乗れば、彼らは：
- 開発せずに実装できる（工数削減）
- 継続収益（運用・保守）を得られる
- 提案の材料（設計フレームワーク・事例）を借りられる

**「開発会社に、受託から脱出する手段を売る」** — これがパートナー勧誘の Big Domino です。

**ただし、パートナーがOneWayを迂回するリスクがあります。** 対策は2つ：

1. **EL3（ライブラリ）と EL2（基盤）がなければ実装できない構造にする** — 部品と土台を握ります
2. **EL5（認定）がなければ顧客に提案できない状態を作る** — 資格で囲います

**着手時期：Phase 2（実績3社と事例が揃ってから）**

**KPI：** パートナー社数 / パートナー経由の成約数 / パートナー1社あたり年間成約額 / 迂回率

**禁則：**
- 事例が3社揃う前にパートナー募集をしない。**売るものがない状態で勧誘すると信用を失います**
- レベニューシェア率を後から下げない。最初から持続可能な率にします

### EL5 — Certification（認定層）

**日本市場において、極めて強力に機能するレイヤーです。**

| 項目 | 内容 |
|---|---|
| **売るもの** | 認定試験 / 認定研修 / 更新料 / 法人認定 |
| **価格** | 受験料 5万円/人 / 研修 30万円/人 / 更新 2万円/年 / 法人認定は EL4 の年会費に統合 |
| **戦略的役割** | **収益商品ではありません。エコシステムの接着剤です** |

**認定の種類：**

| 認定 | 対象 | 意味 |
|---|---|---|
| **OneWay Certified AI Architect** | 顧客企業の社内推進者 | 顧客側に「OneWayの言葉を話せる人」を作ります |
| **Certified Implementation Engineer** | パートナー企業の技術者 | 実装品質を保証します |
| **Certified Partner（Silver / Gold / Platinum）** | パートナー法人 | 認定エンジニア数・実績数で格付けします |

**認定制度の4つの本当の価値（収益は4番目です）：**

| # | 価値 | 内容 |
|---|---|---|
| 1 | **参入障壁** | 認定がなければ実装できない = 供給側のロックイン |
| 2 | **品質保証** | 顧客の購買リスクが下がり、販売の摩擦が消えます |
| 3 | **人材の囲い込み** | 認定を取った技術者は、OneWayエコシステム内でのキャリアを持ちます。転職しても持ち出します |
| 4 | **標準の正統性** | 認定制度の存在自体が「これは標準である」という社会的証明になります |

**日本市場特有の追い風：** 日本企業は資格・認定を強く信頼します。稟議・与信・調達のいずれの場面でも「認定パートナー」という肩書きが実質的に機能します。設立年数の浅さを補う装置として、日本では特に有効です。

**着手時期：Phase 3〜4（パートナー10社・技術者50名規模が見えてから）**

> **早すぎる認定制度は空回りします。** 受験者がいない資格に価値はありません。**需要が先、制度が後**です。

**KPI：** 認定者数 / 認定パートナー社数 / 認定者の在籍企業数 / 更新率

### EL6 — Marketplace（市場層）

**2つの意味があります。混同すると失敗します。**

| | **(a) OneWay Marketplace** | **(b) AWS Marketplace 等への出店** |
|---|---|---|
| 立場 | **胴元** | 出店者 |
| 売るもの | パートナー製エージェント / テンプレート / 実装サービス | OneWay Platform の利用権 |
| 収益 | 取引手数料 15〜20% | なし（手数料を払う側） |
| 目的 | **エコシステムの完成形** | **調達・決裁の摩擦除去** |
| 着手時期 | Phase 5（EL3〜EL5 が揃ってから） | Phase 3 |

#### (b) AWS Marketplace の正しい理解

> **集客チャネルとしてはほぼ機能しません。「調達のOS」として使うのが正解です。**

**AWS Marketplace が示した構造変化（本構想の重要な参照点）：**

```
第1世代：ソフトウェアを売る場
    ↓
第2世代：プロフェッショナルサービスも売れる場
    ↓
第3世代：複数製品を束ねたソリューションを売れる場
    ↓
第4世代：契約型・サブスク型・従量課金を自由に組み合わせられる調達基盤
```

**「ソフトの店」から「エンタープライズIT調達のOS」への変化です。**

OneWay がこれに学ぶべき点：

| 学ぶ点 | OneWayへの適用 |
|---|---|
| サービスも商品として流通させた | パートナーの実装サービスも Marketplace の商材にします |
| 複数製品をソリューションとして束ねた | 基盤 + エージェント + 実装 をワンパッケージで販売します |
| 課金形態を柔軟にした | 契約型 / サブスク / 従量 / 併用を顧客が選べるようにします |
| 調達の摩擦を消すことに価値を置いた | **エコシステムの価値は「品揃え」より「買いやすさ」にあります** |

**出店前の必須確認事項（未確認のまま計画に織り込まないこと）：**

- [ ] 日本法人としての出品者登録要件・必要書類・税務/銀行要件
- [ ] 手数料率（公開リスティングとPrivate Offerで異なり、取引規模でも変動）— **AWSに直接確認**
- [ ] 顧客側のコミット契約への充当可否・充当率 — **顧客のAWS担当に確認させること。「全額充当できます」と営業しない**
- [ ] SaaS課金連携の技術要件と実装工数
- [ ] 入金サイクル（直販より遅くなる。資金繰りへの影響）

#### (a) OneWay Marketplace の成立条件

自社が胴元になる市場は、条件が揃わないと過疎化し、信用を失います。

| # | 条件 | 目標水準 |
|---|---|---|
| 1 | 供給者（パートナー） | 10社以上 |
| 2 | 買い手（導入企業） | 20社以上 |
| 3 | 取引単位の標準化 | EL3のエージェント記述仕様が確立していること |
| 4 | 品質保証の仕組み | EL5の認定制度が稼働していること |
| 5 | 決済・契約の仕組み | レベニューシェア精算が自動化されていること |

**5条件すべてを満たすまで着手しません。** 早すぎるマーケットプレイスは、エコシステム全体の信用を毀損します。

**KPI：** 出品数 / 流通総額（GMV）/ 取引手数料収入 / パートナー製比率

| **Y4** | 2029/09〜2030/08 | + **EL5** | Platform 30社 / ARR 5.8億円 / パートナー15社 / 認定者100名 |

**Y5時点の姿：従業員25名で総売上10.5億円・ARR 8.0億円。** 1人あたり売上4,200万円。
**デリバリーの55%をパートナーが担うため、この人数で成立します。** 受託モデルでは到達不可能な水準です。

## 6. 失敗パターン（順序を間違えると全部壊れます）

| # | 失敗パターン | 何が起きるか | 回避策 |
|---|---|---|---|
| 1 | **EL1を手放す** | 設計を他社に任せると、エコシステムの入口を失い、ただの基盤ベンダーに転落します | **EL1だけは絶対に自社で握る** |
| 2 | **EL3の仕様を決めずに本数を増やす** | 形式がバラバラで資産にならず、EL4もEL6も成立しません | 記述仕様を先に確定します |
| 3 | **売るものがない状態でEL4を募集する** | パートナーが集まらず、募集した事実だけが残って信用を失います | 事例3社・ライブラリ50本の後に募集します |
| 4 | **需要がない状態でEL5を作る** | 受験者ゼロの資格制度になり、制度自体が笑われます | パートナー10社・技術者50名が見えてから |
| 5 | **供給も需要も足りない状態でEL6を開く** | 過疎マーケットプレイスはエコシステム全体の信用を毀損します | 第4章(a)の5条件を厳守します |
| 6 | **EL2で顧客別コードを書く** | 受託に逆戻りし、EL3以降が永久に始まりません | 顧客別コードゼロを社内絶対ルールに |
| 7 | **全レイヤーを同時に立ち上げる** | 人員不足で全部が中途半端になります | 1期に1レイヤーまで |

> **7つのうち最も起きやすいのは「7. 全部同時」です。** 構想が壮大なほど、この誘惑は強くなります。**1期に着手するレイヤーは1つまで**と決めてください。

## 7. 各レイヤーの参入障壁（＝競合が真似できない理由）

| レイヤー | 障壁の種類 | 強度 | 模倣に要する期間 |
|---|---|---|---|
| EL1 Strategy | 実績・フレームワークの正統性 | 中 | 1〜2年 |
| EL2 Platform | 開発工数・運用ノウハウ | 中 | 1〜2年 |
| EL3 Library | **蓄積量 × 標準化** | 高 | 3年以上 |
| EL4 Partners | **関係性（複製不可）** | 高 | 3年以上 |
| EL5 Certification | **社会的正統性・認定者の存在** | 極高 | 5年以上 |
| EL6 Marketplace | **ネットワーク効果** | 極高 | ほぼ不可能 |

**技術は模倣されます。ネットワークと標準は模倣されません。** OneWayの堀は EL3〜EL6 にあります。EL1・EL2 は堀ではなく、堀を作るための入場料です。
